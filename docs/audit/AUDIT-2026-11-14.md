## 2. TUN 模式在 WiFi（非手机热点）下断网 — 根因分析与修复

### 2.1 启动链路（已核实）

`TunTab.vue:25-32` → `configStore.setTunMode`（`stores/config.ts:122-133`）→ Tauri command `set_tun_mode`（`commands/proxy.rs:20-23`）→ `AppController.apply_tun`（事务锁）→ `core::runtime::apply_tun_locked`（`runtime.rs:222-278`）：
1. 持久化 `cfg.tun.enable`；
2. `core.regen_runtime_config()` 重写 `runtime-config.yaml`（`core/config.rs:164`，第 249 行把整个 `app.tun` 序列化进运行时 `tun` 段；`262-291` 在 TUN 开启时强制 `dns.enable=true` 并向 `fake-ip-filter` 注入 NCSI/STUN 域名）；
3. `live_tun_state`（`runtime.rs:282-303`）PATCH `/configs {tun:{…}}` → GET 回读 `tun.enable` 确认；失败回退整进程重启再确认；再失败完整回滚。

TUN 默认值（`config/model.rs`）：`stack=mixed`（381）、`auto_route=true`（384）、`auto_detect_interface=true`（387）、`strict_route=true`（390）、`endpoint_independent_nat=true`（393）、`dns_hijack=[any:53, tcp://any:53]`（396）。
DNS 默认值：`enable=true`、`listen=127.0.0.1:9053`、`enhanced_mode=fake-ip`、`nameserver` 为 DoH（阿里/腾讯，510-514）、`proxy_server_nameserver` 为明文 IP（525-526）、`prefer_h3=true`（484）。
内置规则链（`shared/product.json:20-29`）：`GEOSITE,private,DIRECT` → `RULE-SET,direct` → `ad REJECT` → `ai` / `media` / `proxy` → `GEOIP,CN,DIRECT` → `MATCH,扶梯出行`。

### 2.2 根因候选（按可能性排序，均有代码依据）

| # | 根因候选 | 依据 | 为何「WiFi 断网、热点正常」 |
|---|---|---|---|
| 1 | **`auto_detect_interface=true` 多网卡下选错出站网卡** | `model.rs:340-341`；`core/config.rs:249` 原样透传 | 笔记本 WiFi 下常并存 Wi-Fi / 以太网（未插线仍存在）/ 虚拟网卡（VMware、Hyper-V、WSL、Tailscale 等），mihomo 自动检测可能绑定到非活跃网卡，TUN 建立但流量出不去。手机热点场景通常只有一个活跃物理网卡，检测不会错，故正常。 |
| 2 | **DNS 上游不可达：DoH 默认 + `strict_route=true`** | `model.rs:510-514`（DoH only）、`390`（strict-route）、`262-291`（TUN 时强制 DNS + hijack any:53） | WiFi 路由器/运营商环境可能阻断 `dns.alidns.com` / `doh.pub` 的 DoH（或其 bootstrap 解析 223.5.5.5 被劫持）；strict-route 又把流量强制进 TUN，DNS 全部经 mihomo → 上游不可达 → 全断。热点是另一个运营商路径，可能恰好可达。 |
| 3 | **强制门户（校园/酒店/公司 WiFi）** | `dns_hijack any:53`（396）劫持全部 53 端口；DoH 需先联网认证 | 门户认证前，明文 DNS 被劫持进 mihomo、DoH 又出不去 → 认证页打不开 → 表现为「已连 WiFi 无法上网」。热点无门户，正常。 |
| 4 | **无 Wintun 驱动时 `mixed` 回退 gvisor 兼容性差** | `model.rs:319-322` 注释、381-382 | 部分无线网卡驱动 + 用户态栈组合转发异常；热点场景网卡特征不同可能幸免。 |
| 5 | **IPv6 双栈** | `general.ipv6=false`（109-110）；WiFi 路由器常下发 IPv6 RA，热点较少 | 若 WiFi 的 IPv6 有 RA 但实际不通，部分应用优先 IPv6 → 黑洞。strict-route 理论上压制漏流，但与 #1/#2 叠加时仍可致断。 |

**结论**：#1 与 #2/#3 组合最可能。三者都可通过「连通性探测 + 可操作提示」让用户自助恢复，无需改默认值（避免回归）。

### 2.3 修复方案（不扩展功能）

**P0-1：TUN 应用成功后加一次连通性探测，失败给可操作建议（核心修复）**
- 位置：`core/runtime.rs` `apply_tun_locked` 在 `live_tun_state` 返回 Ok 后调用新增 `probe_tun_connectivity()`；`start_locked` 的 `--clash-edge-enable-tun` 自动开启路径同样接入。
- 探测内容：mihomo 已就绪时，通过控制器探测 `https://www.msftconnecttest.com/connecttest.txt`（该域名已在 `fake-ip-filter` 白名单，`model.rs:493-494`，走真实解析，能同时暴露 DNS 与路由故障）。
- 失败处理：不回滚（避免反复开关抖动），emit `tun-connectivity-degraded` 事件；前端 `TunTab.vue` 渲染黄色横幅，给出三条自助建议：
  1. 关闭「自动检测网卡」，在 `interface-name` 填写当前 WiFi 网卡名（`ipconfig` 查看，如 `WLAN`）；
  2. `stack` 切换 `system` ↔ `gvisor`；
  3. 若处于校园/酒店网络，先用系统代理模式完成门户认证，再开 TUN。
- 理由：Clash Verge Rev 的「TUN 排查向导」本质就是这三步；此处只加反馈，不加功能。

**P0-2：`TunTab.vue` 的 `interface-name` 输入框补充 hint**
- 现状：`TunTab.vue:72-81` 输入框无条件显示，但没有任何「怎么查网卡名」的指引。
- 改动：增加 hint 文案（i18n：`tun.interface_name_hint`）：「留空且开启自动检测时由内核自动选择；TUN 断网时运行 `ipconfig` 查看当前联网网卡名（如 WLAN）并填入」。

**P1：DoH 故障兜底（可选开关，默认不变）**
- `DnsConfig` 增加 `disable_doh: bool`（应用级，不透传 mihomo）：为 true 时 `build_runtime_config` 的 `nameserver` 仅输出明文 IP（复用 `proxy_server_nameserver` 同源地址）。TUN 断网且确认 DoH 被阻断时一键回退。
- `prefer_h3=true`（`model.rs:484`）建议默认改 false：UDP 443 被墙的 WiFi 下 DoH H3 首选会先超时再回退，拖慢首解析；mihomo 官方示例默认不开 H3。

**验证方法**：
1. 复现：Windows 11 + WiFi（路由器）+ 开 TUN → 断网；切手机热点 → 正常。
2. 按 P0-1 探测：断网时应收到 `tun-connectivity-degraded` 事件与横幅。
3. 逐项自助：填网卡名 / 换 stack / 关 strict-route / 关 prefer-h3，观察恢复项。
4. 回归：热点场景、以太网场景、提权重启路径（`relaunch_for_tun`）各跑一遍开关循环。
